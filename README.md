# ShareV

> **Secure, temporary file sharing. No login required.**

ShareV is a serverless, cloud-native file sharing platform built with a security-first architecture. Upload any file, receive a unique 6-character access code, share the code — the recipient downloads the file directly from encrypted cloud storage. All content auto-expires after 24 hours with zero manual cleanup.

**Live demo:** [https://share-v.vercel.app](https://share-v.vercel.app)

---

## What it does

1. **User A** uploads a file (up to 25 MB) via the browser
2. ShareV returns a 6-character alphanumeric access code (e.g. `P25T6J`)
3. **User A** shares the code with anyone — no app, no account needed
4. **User B** enters the code on any device → downloads the file directly
5. After **24 hours** the code expires, the file is deleted, the link dies

No accounts. No email. No tracking. No permanent storage.

## Architecture

```
Browser (React — Vercel CDN)
  │
  │  HTTPS
  ▼
API Gateway
  ├── POST /upload   →  Lambda: sharev-upload
  └── GET  /retrieve/{code}  →  Lambda: sharev-retrieve
                                      │
                        ┌─────────────┴─────────────┐
                        ▼                           ▼
                    Amazon S3                  DynamoDB
                 (encrypted files)         (codes + metadata)
```

**Upload flow:**
1. Browser validates file type and size locally
2. `POST /upload` → Lambda parses multipart body
3. Lambda stores file in S3 at `uploads/{code}/{filename}`
4. Lambda writes metadata to DynamoDB with 24h expiry
5. Returns `{ accessCode, expiresAt }` to browser

**Retrieve flow:**
1. `GET /retrieve/{code}` → Lambda looks up code in DynamoDB
2. Checks expiry manually (never trusts TTL alone)
3. Generates a **15-minute pre-signed S3 URL**
4. Browser downloads file directly from S3 — Lambda never touches the bytes

## Getting Started

### Prerequisites

- Node.js 18+
- npm 9+

### Run locally

```bash
cd frontend
npm install
npm run dev
```

Create `frontend/.env.local`:

```bash
VITE_API_BASE_URL=https://imecvsfr4l.execute-api.ap-south-1.amazonaws.com/dev
```

Open `http://localhost:5173` — connects to the live API.

### Build and deploy

```bash
npm run build     # production build → dist/
npm run preview   # preview locally
npm run lint      # run oxlint
```

Push to `main` — Vercel auto-deploys.

### Deploy a Lambda function

```bash
cd backend/functions/upload
zip -r upload.zip handler.js package.json node_modules/
aws lambda update-function-code \
  --function-name sharev-upload \
  --zip-file fileb://upload.zip \
  --region ap-south-1
```

## Cybersecurity

ShareV was designed around security principles — not patched on afterwards. Every layer has an explicit security rationale.

---

### 1. No User Accounts — Zero PII

ShareV collects nothing about users. No name, email, IP, or device fingerprint is stored.

- **Attack surface reduced** — no credential database to breach
- **No authentication system** — nothing to bypass
- **GDPR by design** — zero personal data means zero compliance burden

---

### 2. Private S3 Bucket — No Public Access

The S3 bucket has all four public access block flags enabled:

```
BlockPublicAcls        = true
IgnorePublicAcls       = true
BlockPublicPolicy      = true
RestrictPublicBuckets  = true
```

Direct object URLs return `AccessDenied`. Files are only accessible via time-limited pre-signed URLs generated by the Lambda.

---

### 3. Pre-Signed URLs — Files Never Proxy Through the Server

When a user retrieves a file, the Lambda generates a **15-minute pre-signed S3 URL** and returns it to the browser. The browser then downloads the file directly from S3.

- The application server **never touches the file bytes** on download
- No opportunity to intercept, log, or modify file content server-side
- Pre-signed URL expires after 15 minutes — useless if intercepted after that window
- `Content-Disposition: attachment` forces browser download, prevents inline execution

---

### 4. AES-256 Encryption at Rest

Every object stored in S3 is encrypted with AES-256 via AWS SSE-S3:

```json
{
  "SSEAlgorithm": "AES256",
  "BucketKeyEnabled": true
}
```

Files are encrypted on disk. AWS manages the keys.

---

### 5. MIME Type Validation — Blocks Extension Spoofing

Client-side validation checks the **actual MIME type** of the file, not just the filename extension. This prevents a common attack where malicious files are renamed (e.g. `malware.exe` → `document.pdf`).

```js
// fileValidation.js
const ALLOWED_TYPES = new Map([
  ['image/jpeg', 'JPEG image'],
  ['application/pdf', 'PDF document'],
  ['text/plain', 'Plain text'],
  // ... etc
])

function validateFile(file) {
  if (!ALLOWED_TYPES.has(file.type)) {
    return { valid: false, error: 'File type not allowed' }
  }
  // ...
}
```

Unsupported MIME types are rejected before upload — the request never reaches the server.

---

### 6. TTL-Based Expiry — Data Minimisation by Design

Files are not deleted manually — the system is architected so data cannot accumulate:

- **DynamoDB TTL** — metadata records auto-delete after `expiresAt` (24h)
- **S3 Lifecycle Rule** — all objects under `uploads/` auto-delete after 2 days
- **Lambda manual check** — retrieve Lambda checks `expiresAt` in code, returns `410 Gone` before TTL deletion even occurs (TTL can lag up to 48h)

Three independent layers ensure nothing persists past its intended lifetime.

---

### 7. Principle of Least Privilege — IAM

Every AWS role and user has the minimum permissions required — nothing more.

**Lambda execution role (`sharev-lambda-role`):**
```json
{
  "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
  "Resource": "arn:aws:s3:::sharev-files-764988199438/*"
},
{
  "Action": ["dynamodb:PutItem", "dynamodb:GetItem", "dynamodb:DeleteItem"],
  "Resource": "arn:aws:dynamodb:ap-south-1:764988199438:table/sharev-files"
}
```

The Lambda cannot list buckets, create tables, or touch any other AWS resource. IAM user `shareV` follows the same pattern — no wildcard `*` resources anywhere.

---

### 8. Security Headers

Every response from the frontend includes a full HTTP security header suite, configured via `frontend/vercel.json`:

| Header | Value | Protects Against |
|--------|-------|-----------------|
| `Content-Security-Policy` | `default-src 'self'; connect-src 'self' https://*.amazonaws.com` | XSS, data injection |
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains; preload` | HTTPS downgrade attacks |
| `X-Frame-Options` | `DENY` | Clickjacking |
| `X-Content-Type-Options` | `nosniff` | MIME sniffing |
| `X-XSS-Protection` | `1; mode=block` | Reflected XSS (legacy browsers) |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | URL leakage to third parties |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` | Unauthorised hardware access |

---

### 9. Cryptographically Random Access Codes

Access codes are generated using Node.js `crypto.randomBytes()` — not `Math.random()`, which is not cryptographically secure.

```js
import { randomBytes } from 'crypto'

function generateAccessCode() {
  const chars = 'ABCDEFGHJKLMNPQRSTUVWXYZ23456789' // no 0/O or 1/I (ambiguous)
  const bytes = randomBytes(6)
  return Array.from(bytes, b => chars[b % chars.length]).join('')
}
```

- Charset excludes visually ambiguous characters (`0`, `O`, `1`, `I`)
- ~1 billion possible codes — brute force impractical within the 24h window
- `ConditionExpression: attribute_not_exists(accessCode)` on DynamoDB write prevents collision

---

### 10. Structured Logging + Alerting

Both Lambda functions use structured JSON logging queryable in CloudWatch Insights:

```json
{ "level": "INFO", "message": "Upload complete", "accessCode": "P25T6J", "fileName": "report.pdf", "fileSize": 204800 }
{ "level": "ERROR", "message": "Upload failed", "error": "No file part found in multipart body" }
```

CloudWatch alarms fire an SNS email alert when either Lambda errors **≥3 times in any 5-minute window** — providing real-time visibility into attacks or failures.

---

### 11. MFA on Root Account

The AWS root account has MFA enabled. Day-to-day operations use the `shareV` IAM user with scoped permissions. Root credentials are never used programmatically.
